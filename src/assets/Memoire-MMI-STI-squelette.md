# §7 — LA PROBLÉMATIQUE (3 candidates entièrement développées)

> **Thématique** (large, en quelques mots) : *le développement d'un système d'information métier sur-mesure dans une PME*. La **problématique** est la question précise posée dessus.

### ⭐ Candidate n°1 (recommandée)
**« Dans quelle mesure le développement d'un ERP web sur-mesure répond-il mieux aux besoins métier spécifiques d'une société d'interprétation que les solutions génériques du marché ? »**
- **Pourquoi elle est bonne** : technique + métier + esprit critique ; très MMI ; permet de comparer (sur-mesure vs SaaS/progiciel) et de nuancer (limites du sur-mesure).
- **Sous-questions** : Quels besoins de STI sont vraiment spécifiques (Chorus, GHU, TraduitPro, tarifs, rôles) ? Qu'est-ce qu'une solution générique ne sait pas faire ? À quel coût (dev, maintenance, dépendance) le sur-mesure devient-il pertinent ?
- **Plan Partie 2** : Variante A.

### Candidate n°2
**« Dans quelle mesure l'automatisation des processus (saisie des missions, facturation) au sein d'un ERP interne transforme-t-elle l'organisation et la fiabilité du travail chez STI ? »**
- **Angle** : automatisation (n8n e-mail→mission, facturation auto, rappels) + conduite du changement + fiabilité/contrôle.
- **Sous-questions** : Que gagne-t-on en temps/erreurs ? Que perd-on en contrôle ? Comment garder « l'humain dans la boucle » ?
- **Plan Partie 2** : Variante B.

### Candidate n°3
**« Dans quelle mesure une conception mobile-first et adaptée aux rôles métier améliore-t-elle l'appropriation d'un outil de gestion par ses utilisateurs ? »**
- **Angle** : UX/UI, ergonomie métier, adoption.
- **Sous-questions** : Pourquoi un même outil ne convient pas à tous les rôles ? Comment mesurer l'adoption ? Quels arbitrages simplicité/puissance ?
- **Plan Partie 2** : Variante C.

**Construction académique (à intégrer en début de Partie 2, quelle que soit la candidate)** : préciser le **domaine** (systèmes d'information / développement web), le **thème** (ERP sur-mesure en PME), le **problème** (la question), les **objectifs**, la **portée/retombées** (pour STI et au-delà), et appuyer sur une **recension des écrits** (cf. §13).

# §11 — Partie 2 : développement (≈ 8 p. max)

### Si problématique n°1 (Variante A)
- **2.1 Analyse** : les besoins **spécifiques** de STI qu'un outil générique couvre mal — types de clients (Chorus/GHU/TraduitPro/TA), tarifs particuliers, conformité Chorus Pro, rôles métier, volumétrie.
- **2.2 Diagnostic** : limites des solutions génériques/SaaS (rigidité, coût d'adaptation, données sensibles, dépendance éditeur) et de l'ancien outil.
- **2.3 Actions/résultats** : ce que le sur-mesure a permis (modèle de données métier, automatisations, UX par rôle, déploiement maîtrisé) + **résultats** `[gain de temps de saisie, réduction d'erreurs de facturation, adoption par les équipes — chiffre si possible]`.
- **2.4 Limites/recul** : maintenance, **dépendance à un développeur unique**, dette technique, sécurité/RGPD, soutenabilité.

### Si problématique n°2 (Variante B)
- 2.1 Processus avant automatisation (saisie manuelle des missions depuis les e-mails, calculs de facturation manuels).
- 2.2 Où l'automatisation crée de la valeur (temps, régularité) **et** du risque (erreurs propagées, perte de vigilance).
- 2.3 Automatisations mises en place (n8n e-mail→mission, calculs/contrôles de facturation, rappels) + effets mesurés.
- 2.4 Garder l'humain dans la boucle : contrôles, validations, garde-fous ; limites.

### Si problématique n°3 (Variante C)
- 2.1 Des rôles aux besoins hétérogènes (coordination vs facturation vs recrutement).
- 2.2 Pourquoi un outil « pour tous » échoue à être adopté (surcharge, non-pertinence).
- 2.3 Conception mobile-first + dashboards par rôle + ergonomie métier (exemples concrets).
- 2.4 Mesure de l'adoption (usage, retours utilisateurs) ; limites (maintenance de N vues, cohérence).

> À la fin : on doit **sentir que la problématique est traitée**, avec des **réponses argumentées** (pas une question posée puis évacuée).

# §15 — Tables & Glossaire

**Tables** : table des illustrations (titre, n° figure, page) + table des annexes.

**Glossaire (interactif) — termes par ordre alphabétique (rempli, complète si besoin)** :
- **API** : interface de programmation permettant à deux logiciels de communiquer (ici, le front Angular dialogue avec l'API Spring Boot).

- **Chorus Pro** : plateforme publique obligatoire de facturation électronique vers le secteur public (via PISTE).
- **CI/CD** : intégration et déploiement continus (automatisation des tests et mises en production).
- **Conteneur / Docker** : technologie d'empaquetage d'une application et de ses dépendances pour la déployer de façon reproductible.
- **Dashboard (tableau de bord)** : écran synthétique d'indicateurs, ici personnalisé par rôle.
- **Dette technique** : coût futur induit par des choix de développement rapides/temporaires.
- **ERP** *(Enterprise Resource Planning)* : progiciel/outil de gestion intégré couvrant les processus de l'entreprise (missions, facturation, etc.).
- **Front-end** : partie visible/cliquable de l'application (interface utilisateur).
- **GHU** : `[type de client/secteur — à préciser dans ton contexte STI]`.
- **JWT** : jeton d'authentification sécurisant l'accès à l'API.
- **Mobile-first** : conception pensée d'abord pour le mobile, puis adaptée au desktop.
- **n8n** : outil d'automatisation de workflows (ici : e-mail → création de mission).
- **PostgreSQL** : système de base de données relationnelle utilisé par l'ERP.
- **REST** : style d'architecture d'API web (verbes HTTP, ressources).
- **SaaS** *(Software as a Service)* : logiciel générique loué en ligne (vs solution sur-mesure).
- **Smart/Dumb components** : pattern Angular séparant composants « intelligents » (état/services) et « présentationnels » (affichage).
- **Spring Boot** : framework Java pour construire l'API back-end.
- **Sur-mesure** : application développée spécifiquement pour les besoins de l'entreprise (vs progiciel générique).
- **TraduitPro / TA / Chorus** : `[types de clients STI — précise leurs spécificités tarifaires]`.
- **UX / UI** : expérience utilisateur / interface utilisateur (ergonomie, design).

# §18 — FAQ / scénarios (tous les cas)

- **« C'est un stage, pas une alternance »** → remplace « alternance » par « stage » et adapte les dates ; la structure ne change pas.
- **« Je manque d'idées »** → relis ton journal de bord et la liste des 6 missions (§9) ; choisis celles qui posent une vraie **question**.
- **« Ma problématique est trop large »** → resserre avec « Dans quelle mesure » + un périmètre précis (un type de client, un processus). **Trop étroite** → élargis la thématique au-dessus.
- **« Peur de me répéter avec le rapport de stage de l'an dernier »** → ici tu **synthétises** le factuel (Partie 1 courte) pour aller vers la **réflexion** (Partie 2) : ce n'est pas un rapport chronologique.
- **« Comment citer ? »** → entre guillemets + renvoi à la biblio (cf. §13). Jamais de copier-coller non sourcé.
- **« Quelle longueur ? »** → respecte les volumes indicatifs ; mieux vaut **dense et structuré** que long et délayé.
- **« Quand rédiger en travaillant ? »** → commence **dès maintenant** ; note les questions au fil de l'eau ; utilise les créneaux non encadrés.
